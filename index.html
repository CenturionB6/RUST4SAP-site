Rust · SAP · ABAC · no RFC SDK

Let AI agents read SAP without handing them the keys.

AI agents request. Rust enforces. ABAC decides. SAP executes.
RUST4SAP is a Rust gateway between AI assistants and SAP. The server decides what each user's agent may see from the user's attributes, and the model only ever receives the result — filtered rows, projected fields, or a refusal with the rule that caused it. Built on OData and IDoc, with no proprietary runtime and no RFC SDK.

Today it runs against a mock SAP connector: the ABAC engine, MCP server and audit chain are real and tested, the SAP connection is not.

The problem

An agent connected to SAP sees everything the account can see.

Give an AI assistant a service account and it inherits the account's reach. Every question it asks is answered with the same breadth, whether the person behind it is a buyer who should see a partner's name, or a controller who may also see its bank details. Prompt injection makes it worse: the attacker does not need the credentials, only a sentence that changes the question. And once a record is in the model's context, it may have left your perimeter.

An API gateway does not fix this. It authenticates the caller and rate-limits them, but it does not know that clearance buys sensitivity and not geography. That knowledge has to sit in the path between the agent and SAP, and it has to be enforced somewhere the model cannot argue with.

How it works

Four steps, one of which the model cannot influence.

1 · The agent asks

An MCP tool call arrives with the employee's delegated token and the client's token.

2 · Rust verifies

Signature, issuer, audience, expiry, delegation binding — then entitlements are resolved from the authoritative source. Only then does a subject exist.

3 · ABAC decides

Deny by default. Rules from the employee's attributes decide which entity, which region and which fields, and every rule records why it matched or did not.

4 · SAP executes

Only an allowed request reaches the connector. Fields outside the grant are projected away before the model sees a byte, and the decision is written to the audit chain first.

About

Why a gateway, and why Rust.

SAP holds the records a company runs on, and the two open paths into it are OData and IDoc. Everything else — RFC, BAPI, middleware — needs a proprietary SDK, a JVM, or a licence. A gateway that decides what each agent may read has to be designed to sit in the request path. It should make its boundary clear enough for a security team to inspect and operate with confidence.

Why Rust

Designed to enforce authorization in the request path. One static binary, no runtime beside SAP, no garbage collector between the request and the answer. A documented Rust implementation with 134 tests, 37 of them public: the policy engine and those tests can be read and run, rather than taken on trust.

Who it is for

Platform and security teams putting an assistant in front of SAP; integration engineers who need OData and IDoc without a middleware licence; SAP developers who want JSON on stdout and a meaningful exit code.

The foundation: OData and IDoc.

SAP speaks many protocols. Only two of them are open enough to build on without a licence negotiation.

OData

HTTP and JSON. Read $metadata, list entity sets, query collections with $top, $select, $filter, $orderby. Basic auth over rustls — no OpenSSL on the host.

cargo run -- odata --root $SAP_ODATA_ROOT metadata

IDoc

XML documents with numbered segments. Parsed into a typed tree, or flattened to SEGMENT-FIELD pairs for loading. Malformed input fails closed.

cargo run -- idoc order.xml --flat

Threat model

What the gateway is for, and what it is not.

It protects against

A model that is talked into asking for more than the user may see. Prompt injection can change what the agent requests; it cannot change the attributes the server decides from. Over-broad queries are refused, fields outside the grant are projected away, and rows outside the user's region never enter the model's context.

It does not protect against

A compromised SAP account, a malicious policy author, or an operator who can restart the gateway with different configuration. The audit chain is tamper-evident only when a copy is retained elsewhere. A stolen bearer token is replayable until it expires — sender-constraining is planned, not implemented.

How it differs

Not an API gateway, not a generic MCP server.

  • ·vs. SAP's own tooling. No RFC SDK, no JVM, no middleware licence. One binary that reads OData and IDoc, and refuses what it cannot do.
  • ·vs. a generic MCP server. Most MCP servers forward whatever the model asks for. This one treats the model as untrusted and answers from attributes, not from the prompt.
  • ·vs. an API gateway. An API gateway authenticates callers and rate-limits them. It does not know that a buyer may see a business partner's name but not its IBAN, or that clearance buys sensitivity but not geography.

Limits

What it refuses, and what that costs you.

A tool is defined by its limits. These are deliberate, and each has a price.

  • ✕RFC, BAPI and IDoc sending. Only OData reads and IDoc parsing. Cost: if your integration needs RFC, this is the wrong tool and will stay wrong.
  • ✕Silent partial reads. Malformed XML is an error, not a half-parsed tree. Cost: a truncated IDoc stops a pipeline that a lenient parser would have let through — deliberately.
  • ✕A live SAP connection today. The connector is a mock; no SAP system has been contacted. Cost: you cannot evaluate it against your own landscape yet — only the policy engine and 37 tests are checkable.
  • ✕A middleware replacement. No orchestration, retries or mapping across fifty interfaces. Cost: if that is the job, buy the middleware.
  • ✕Sender-constrained tokens. DPoP is planned, not built. Cost: a stolen bearer token is replayable until it expires.

Use it

Try the public extract with no account; the gateway needs access.

quickstart 
# no account needed: the policy engine and its tests are public
git clone https://github.com/CenturionB6/rust4sap-samples
cd rust4sap-samples && cargo test
→ 37 passed

# the gateway itself is in the private repository — request access, then:
git clone git@github.com:CenturionB6/RUST4SAP.git && cd RUST4SAP

# the CLI crate (rust4sap) builds in ./target
cargo build --release
# the gateway is its own workspace, with its own target directory
(cd mcp && cargo build --release)

./mcp/target/release/rust4sap-mcp --issuer $ISS --audience $AUD \
  --jwks $JWKS --entitlements $ENTS --http 127.0.0.1:8080

# the readers underneath it live in the outer crate
./target/release/rust4sap odata service
./target/release/rust4sap idoc docs/order.xml
  1. Rust 1.98 (developed and tested on 1.98.0) and a C toolchain — nothing else. Built on macOS; Linux and Windows are the target platforms.
  2. Credentials from flags or environment, never a config file in the repo.
  3. Output is JSON on stdout, so it pipes straight into jq or a queue.
  4. Exit codes are meaningful: a non-zero status means the read failed.
